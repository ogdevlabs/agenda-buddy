ABSORBED FROM F-018 T18 at the Plan approval gate 2026-08-18 - the EIGHTH F-018 task pulled into F-016, added because the readiness party found the feature's central claim was unenforced.
WHY THIS EXISTS. F-016's whole argument is 'endpoint authorization you can demonstrate' - that is why it absorbed six harness tasks instead of shipping unit tests. Without a CI job the demonstration runs on one developer's laptop and nothing enforces it on a push or PR. Echo's framing at the readiness party: the failure mode is not 'tests do not run', it is that they run UNTIL SOMEONE STOPS RUNNING THEM AND NOTHING NOTICES.
Add a SEPARATE CI job (not folded into the existing api job) running the integration suite. Blocking from run 1. Enforce a duration budget rather than hoping for one - container startup is a measured 4.45s warm and the job runs container-per-class.
The existing pipeline is PATH-FILTERED and triggers only on push to main or PR to main, so this job will not run on ordinary branches. That is the same trap that let F-013's 'assert every service starts' guard sit unexecuted until it first ran - and first failed - on PR #35.
CANNOT BE VERIFIED LOCALLY. Needs a real CI run on a short-lived throwaway branch PUSHED BY THE MAINTAINER on request; main is PR-protected. F-018's readiness party logged this class of dependency as 'dependency-missed' because the task graph cannot express 'waits on a human'. Do not schedule this like an ordinary task.
DOES NOT amend CONSTITUTION section 7 to require the Integration gate - that is gated on 10 consecutive green runs and tracked separately (F-018 T04, NOT absorbed).
