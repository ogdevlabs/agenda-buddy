Corrects every row in api-contracts.md §2's route table: api/v1/ prefixes added, verbs matched to what each backend route actually accepts, payload shapes matched to each route's real DTO. Includes the routes F-014 added (session notes, messages, notifications, provider report, provider deactivation, payments) that MobileApp has never called at all.
The one behavioral change, not just a path fix: BookingApiService.UpdateStatusAsync's PUT-based call (which F-014 now ignores entirely) is replaced by POST api/v1/booking/appointments/{identifier}/status. Per ux-review.md finding 3, the customer-facing "mark complete" control must be hidden entirely at render time (a role check), not rendered disabled — a disabled button with no explanation is worse than no button.
Depends on F-015-T06 (the corrections land in the newly-extracted, testable classes, not back into the untestable ones) and F-015-T05 (needs a real gateway + backend to verify against, per AC2's "verified against a live AppHost").

## Closed 2026-08-23

Every row in `api-contracts.md` §2 was corrected in `MobileApp/Routing/*.cs` (`BookingRouteBuilder`,
`CalendarRouteBuilder`, `CustomerRouteBuilder`, `MessagingRouteBuilder`, `NotificationRouteBuilder`, plus a
new `ProviderRouteBuilder`), with each corresponding `MobileApp.Tests/Routing/*Tests.cs` re-pinned to the
corrected value. Six previously-unreachable F-014 capabilities were wired for the first time: session
notes (GET/POST/PUT), payments (GET/POST), provider report and provider deactivation — each via a new or
extended `*ApiService` method (`ProviderApiService` is new; `BookingApiService` gained notes/payment
methods). `MessagingApiService`/`NotificationApiService`'s mark-read calls were corrected from `PATCH` to
`POST` (the real routes only accept `POST`), and both now tolerate the real `204 No Content` success body
instead of assuming an updated entity is returned.

**AC7 — the status-route swap.** `BookingApiService.UpdateStatusAsync` now calls
`POST api/v1/booking/appointments/{identifier}/status` with `{"status": "…"}`, replacing the legacy `PUT
booking/{id}` call. `AppointmentDetailViewModel` gained a `ShowCompleteButton => _session.IsProvider`
property gating both the Complete button's XAML `IsVisible` binding and its `RelayCommand`'s `CanExecute` —
the control is absent from the visual tree and the command is unavailable for a customer session, not
merely disabled (ux-review.md finding 3). Covered by new ViewModel tests
(`ShowCompleteButton_CustomerSession_IsFalse`, `CompleteCommand_CustomerSession_CanExecuteIsFalse`, and
their provider-session controls).

**AC2 — proof against a live backend.** F-014's own integration suite (`PaymentsAndStatusTest`,
`SessionNotesTest`, `ReportAndDeactivationTest`, `MessagingAndNotificationsTest`, `CalendarOwnershipTest`,
`CustomerListRoleTest`) already exhaustively covers every corrected path string's authorization behaviour.
New to this task: `AgendaBuddy.IntegrationTests/Harness/MobileClientRouteResolutionTest.cs`, which adds a
`ProjectReference` to `MobileApp.csproj` and builds real HTTP requests directly from
`MobileApp.Routing.*RouteBuilder` output (not a hand-written path string duplicated in the test project),
firing them at `Booking`/`Calendar`/`Customer`/`Provider` hosted over real HTTP. 13 new tests, all green —
proving the corrected client code itself resolves, not just that the design doc's path strings do.

**Deviation from `api-contracts.md` §2 (recorded, not silently followed).** The doc's `BookingApiService`
rows (`GET api/v1/booking/appointments?from=&to=` and `.../appointments/{identifier}`) do not match
reality: `Booking/Program.cs` has no GET route for an appointment, list or single, and never has —
confirmed against the live route table, not inferred. Following the doc literally would 404 against a
real backend, failing AC2's own wording ("not a 404"). Since the PRD is explicit that this feature adds no
new backend routes, `BookingApiService.GetTodayAppointmentsAsync`/`GetAppointmentAsync` were instead
rewired to compose with `ICalendarApiService.GetAppointmentsAsync()` — Calendar's real
`GET api/v1/calendar/appointments/{email}` is the only GET that actually exists for this data. Filtering to
"today" and finding a single appointment by id now happens client-side. `CalendarApiService`'s parsing
deliberately avoids ever binding Calendar's `id`/`_id` field (Calendar does not register
`ObjectIdJsonConverter`, unlike Booking/Customer/Provider — filed, pre-existing debt), using the plain-string
`identifier` field instead, so a real response never crashes client-side deserialization.

**Other known gaps, called out rather than fixed (out of this task's route/verb/payload scope):**
- `AppointmentDetailPage`'s "Cancel" action still sends `AppointmentStatus.Cancelled` to the new status
  route, which does not accept it as a target (only `Booked`/`Completed`) — it will now get a real,
  correctly-typed `400`/`409` instead of silently succeeding against the old wrong-shape `PUT`. Cancelling
  is really Booking's `DELETE /appointments/` route; wiring it is new client functionality, filed as a
  follow-up. "Confirm" was remapped to `AppointmentStatus.Booked`, the real legal transition.
- `MessagingApiService.GetThreadAsync`'s parameter is now documented as the counterpart's *email* (the real
  route's key), not an opaque thread id — `MessageThreadViewModel` still passes its fabricated `ThreadId`;
  wiring the ViewModel to pass a real email is `SeedDataProvider` removal's concern (F-015-T08).
- Field-level mapping between backend entities (`AppointmentEntity`, `CustomerEntity`) and the client's own
  DTOs (`AppointmentSummary`/`AppointmentDetail`/`CustomerSummary`) is best-effort, not exhaustive — those
  DTOs predate this task and diverge from the entities' real shapes (e.g. `ScheduledAt` vs `Start`); full
  fidelity is a larger data-shape reconciliation likely belonging to F-015-T08's real-data wiring, not this
  route-correction task.
