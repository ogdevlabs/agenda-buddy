A new ASP.NET Core Minimal API project, `Gateway/`, following the exact shape of the seven existing services: `builder.AddServiceDefaults()`, `app.UseAgendaBuddyTransportSecurity()` before auth (there is no auth here, but the middleware-order test in Library.Tests scans every service's Program.cs, so this must match), `app.MapDefaultEndpoints()` for `/health` and `/alive`. No YARP, no routing yet — this task only proves the eighth process starts, reports healthy, and exports telemetry the same way the other seven do (inheriting `PiiRedactingProcessor` automatically, per threat T-NL-3).
No AppHost wiring yet (F-015-T05) — this is a standalone project that can build and run with `--no-launch-profile` before it is a graph member.

**Built (2026-08-23).** Created `Gateway/Gateway.csproj` (net10.0, `Microsoft.NET.Sdk.Web`, the only
`ProjectReference` is `AgendaBuddy.ServiceDefaults` — no MongoDB.Driver, MediatR, or auth package, since
there is no persistence, business logic, or auth middleware yet), `Gateway/GlobalUsings.cs` (`global using
AgendaBuddy.ServiceDefaults;`, matching the other seven services' pattern for reaching
`AddServiceDefaults`/`UseAgendaBuddyTransportSecurity`/`MapDefaultEndpoints` without a local `using`), and
`Gateway/Program.cs` — exactly the three calls specified: `builder.AddServiceDefaults()`,
`app.UseAgendaBuddyTransportSecurity()` immediately after `Build()`, `app.MapDefaultEndpoints()`, then
`app.Run()`. No YARP, no routing, no `appsettings.json` — pure scaffold.

Added `Gateway/GatewayAnchor.cs`, a small `public sealed class` with a private constructor, whose only
purpose is to be a public type in the Gateway assembly for
`WebApplicationFactory<TEntryPoint>`/`EntryPoints.cs`-style hosting — the seven domain services reuse
their `*.Configuration(s).MongoDbConfiguration` type for this, and Gateway has no such type to reuse.
(First attempt made it `static`; `WebApplicationFactory<T>` requires `T : class` with an instantiable
type, so `static class` fails `CS0718` — fixed to a non-static sealed class with a private constructor.)

Added `Gateway` to `agenda-buddy.sln` (via `dotnet sln add`, so the GUID/config-platform boilerplate is
generated correctly) and to `agenda-buddy-backend.slnf`, so it now builds and is covered by the normal
backend build/test commands.

**Middleware-order test updated, not just re-pointed at a list.** Read
`Library.Tests/Security/TransportSecurityOrderTest.cs` first, as instructed — it enumerates the seven
services by an explicit array (`AllServices`, renamed from `Services`) AND discovers `Program.cs` files on
disk (`EveryServiceProgramFile_IsAccountedFor`, renamed from `EverySevenServices_AreAccountedFor`), so
adding `Gateway/Program.cs` without touching this test would have made that discovery test fail (actual
would be 8 directories, expected 7). Added `"Gateway"` to the array. Gateway has no
`app.UseAuthentication()` call to be ordered against (no auth middleware — ARCHITECTURE.md §2's "Auth
passthrough"), so it could not simply join the two seven-service `[Theory]`s
(`TransportSecurity_IsRegisteredBeforeAuthentication`, `NoService_CallsUseHttpsRedirectionDirectly`) —
doing so would have made the authentication-relative assertion fail for a service that will never call
`UseAuthentication`. Instead added a new `[Fact] GatewayCallsTransportSecurity` asserting the two things
that do apply to Gateway: the call is present, and `UseHttpsRedirection` is never called directly.

**Testability, per the task's guidance.** Deliberately did **not** use `ServiceHostFixture<TEntryPoint>`
for the hosted test — that fixture starts a MongoDB Testcontainer and exports `JWT_PUBLIC_KEY` before the
host builds, both in service of dependencies (`IMongoClient`, `AddAgendaBuddyAuthentication`) Gateway's
`Program.cs` does not have. Using it anyway would have paid a ~3-4s container-startup cost to test
infrastructure this process never touches, and would misrepresent what F-015-T01 actually built. Added
`AgendaBuddy.IntegrationTests/Harness/GatewayHostTest.cs` using a plain
`WebApplicationFactory<GatewayAnchor>` instead — real HTTP through the real pipeline, same anchor-type
pattern as the seven services (see `EntryPoints.cs`), just without the container lifecycle. Two tests:
`GetHealth_ReturnsHealthy` (asserts `200 OK` and body `"Healthy"`) and `GetAlive_ReturnsOk` (asserts
`200 OK`). Added the `Gateway.csproj` `ProjectReference` and a `GatewayAnchor` global-using alias to
`AgendaBuddy.IntegrationTests.csproj` / `GlobalUsings.cs`.

**Deliberately did not add Gateway to `Harness/EntryPoints.cs`.** That file and
`Harness/InternalsVisibleToTest.cs` together pin F-016 AC-2 — an invariant specific to "the seven
services" (hardcoded counts of 7, an `AllSevenServices_AreReferencedAndDistinct` fact, and an assertion
that every one of the seven grants `InternalsVisibleTo` to this test project for asserting on internal
helpers). Gateway has no internal helpers to expose and is not one of the seven AC-2 services; folding it
into that list would have required adding `InternalsVisibleTo` to `Gateway.csproj` for no reason and
bumping every hardcoded "7" to "8", which conflates an eighth process's scaffold test with a different
task's acceptance criterion. `GatewayAnchor` is referenced directly from `GatewayHostTest.cs` instead.
