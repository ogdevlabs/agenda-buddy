Builds the route/cluster config programmatically from Aspire service-discovery keys (`services__<name>__http__0`) per the approach F-015-T02's spike confirmed — not a static YARP cluster file, which could drift from what `AppHostWiring.cs` actually wires. One route per service, matching `api/v1/{service}/**`, including `api/v1/auth/**` and the root-mapped `/device-token` → identity. No path rewriting.
Threat T-302 (threat-model.md, mitigate now): the route table must be an explicit allowlist, never a catch-all forward — this is the task that makes ARCHITECTURE.md §2's design decision real rather than aspirational, and the [security] AC above is what the build TDD gate demands a failing-first test for (issue #55).

**Closed 2026-08-23.** TDD followed as required: `AgendaBuddy.IntegrationTests/Harness/GatewayRoutingTest.cs` was written and run first against F-015-T02's still-single-destination provider — confirmed red (17 route-table/proxy-attempt failures + 3 security-test failures, the latter specifically because ASP.NET's default "no endpoint matched" 404 carries no `application/problem+json` body). Then implemented and confirmed green (19/19).

`AspireServiceDiscoveryProxyConfigProvider`'s `_destinationNames` (single `"booking"`) was replaced with an explicit `_routeSpecs` allowlist — `(ServiceName, RouteId, PathPattern)` tuples, one per YARP route, resolved per-service into its own `ClusterConfig`/`DestinationConfig` from the same `services:<name>:http:0`/`https:0` Aspire service-discovery keys the spike already read. Final route table:

| Path pattern | Cluster |
|---|---|
| `/api/v1/booking/{**catch-all}` | `booking` |
| `/api/v1/calendar/{**catch-all}` | `calendar` |
| `/api/v1/customers/{**catch-all}` | `customer` |
| `/api/v1/providers/{**catch-all}` | `provider` |
| `/api/v1/services/{**catch-all}` | `services` |
| `/api/v1/professions/{**catch-all}` | `profession` |
| `/api/v1/auth/{**catch-all}` | `identity` |
| `/device-token` (exact, root-mapped) | `identity` |

Prefixes were verified against `docs/pdlc/context/01-api-surface.md` rather than assumed from the Aspire logical name — `customer`/`provider`/`profession` route under the **plural** `customers`/`providers`/`professions` groups their own services actually register; `identity` gets two routes (its own `auth` group plus the one route in the solution mapped outside the `api/v1/` convention, `POST /device-token`) sharing one cluster. A service whose address cannot be resolved contributes no route at all — never a route pointing nowhere — so it falls through to the same no-match path as any other unconfigured request until Aspire supplies the key.

`Gateway/Program.cs` gained `app.MapFallback(HandleNoRoute)` after `app.MapReverseProxy()` — the lowest-priority endpoint in the pipeline, reached only when no YARP route (and neither of `/health`/`/alive`) matched. It returns the `gateway-no-route` `ProblemDetails` shape from `api-contracts.md` §1 (`type: https://agendabuddy.dev/errors/gateway-no-route`, `status: 404`, `requestId` from `Activity.Current`), scoped narrowly to the no-match case — a matched-but-unreachable destination (5xx/timeout) is explicitly left to F-015-T04.

The security test is `AgendaBuddy.IntegrationTests.Harness.GatewayNoRouteTest.T302_UnmappedPath_Returns404NotProxied` (`[Theory]`, three probe paths: a backend's own bare `/health` reached through the gateway without the `api/v1/booking/**` prefix, a typo'd/unconfigured `api/v1/nonexistent/probe`, and the pre-F-015 broken `/booking` path with no `api/v1` prefix at all). It asserts 404 + `application/problem+json` + the exact `gateway-no-route` `type`/`title`/`status`, that `detail` names the offending path, and that `requestId` is present. `GatewayRoutingTest` covers the seven-prefix allowlist itself: one set of theory cases reads the real `IProxyConfigProvider` singleton out of the DI container against fake (unreachable) per-service addresses and asserts each `RouteConfig`'s exact path pattern and each `ClusterConfig`'s destination address (plus the two-routes-one-cluster identity case, and a "exactly seven clusters" completeness check); a second set makes live HTTP requests against each allowlisted prefix and asserts the response is never a 404 (i.e., the request was routed, not rejected) — no real backend is required since a connection-refused failure downstream is still distinguishable from "no route matched."
