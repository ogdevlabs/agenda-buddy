The gating risk from Adversarial finding #4 and ARCHITECTURE.md §6: build a custom `IProxyConfigProvider` that re-reads `IConfiguration` (the Aspire service-discovery keys `AddServiceDefaults()` already resolves) on each YARP config-reload cycle. Restart one backend service under a running AppHost; confirm the gateway routes to the new port WITHOUT the gateway process restarting.
Measure and record the added latency (NFR in the PRD) — this project's standing discipline is to measure rather than assume (F-021's 262ms BCrypt measurement is the precedent).
This is a spike, not shippable code by itself — its output is a go/no-go decision for F-015-T03's implementation approach, and the measured latency number for the PRD's NFR section. If the spike fails (YARP cannot re-resolve without a full restart), record the fallback from ARCHITECTURE.md §6 (a WaitFor-triggered gateway restart on backend-resource transition) and adjust F-015-T03 accordingly — do not silently ship the failed approach.

**Closing findings (2026-08-23):** Go, with a corrected mechanism. Built `Gateway/AspireServiceDiscoveryProxyConfigProvider.cs`, a custom `IProxyConfigProvider` that reads `services:<name>:http:0`/`:https:0` from `IConfiguration` and re-polls every 2 seconds, wired into `Gateway/Program.cs` (`AddSingleton<IProxyConfigProvider, ...>()` + `AddReverseProxy()` + `MapReverseProxy()`), `Yarp.ReverseProxy` 2.3.0 added to `Gateway.csproj`, and a minimal `WithReference(booking)`/`WaitFor(booking)` wiring added to `AgendaBuddy.AppHost/AppHostWiring.cs` (F-015-T05 will supersede this with the full seven-service wiring — flag for merge coordination). Ran a real AppHost (Rancher Desktop docker, MongoDB + Kafka containers), used `aspire resource booking restart` twice to force two independent dynamic-port reassignments (confirmed via `aspire describe booking --format Json`: Booking's Kestrel port moved 52846 → 52995 → 53146), and confirmed via `curl` that the Gateway (same OS process throughout, confirmed via `ps -p`) kept routing correctly to Booking after each restart, with matching `405 ProblemDetails` bodies before/after. Root cause, evidenced via `aspire logs gateway`: Aspire's DCP orchestrator fronts every `WithReference`-injected address with its own stable local proxy port (Booking's `services__booking__http__0` stayed `http://localhost:52767` across both restarts even though Booking's real Kestrel port changed twice) — so the destination address never actually goes stale under this project's wiring, independent of whether the custom provider polls at all. The poll loop is kept as a correct defense against that changing, but budget zero engineering time in F-015-T03 toward a more aggressive invalidation strategy. Latency (20 requests/path, loopback, first request excluded): direct-to-Booking's-own-port ~0.38ms, direct-to-Aspire's-service-discovery-address (no gateway) ~0.95ms, through-the-Gateway ~0.86ms — the Gateway/YARP hop itself adds no latency measurably distinguishable from the address every service already resolves today. Full evidence and gotchas recorded in `docs/pdlc/design/api-gateway-and-mobile-contract/ARCHITECTURE.md` §6 (also updated §2/§5 to stop saying "pending spike"). All 452 backend tests pass unchanged; `AgendaBuddy.AppHost.Tests`' `AddApi` helper signature changed from `void` to returning the resource builder (needed to capture `booking` for the reference) with no behavior change for the seven existing services.
