run-ios.sh already discovers each service's dynamically-assigned port by probing /alive across every port a PID listens on — today it only prints the result for a human. Extends the same probe loop to also find the gateway's port, and injects it into the simulator process as MAUI_API_BASE_URL, which MauiProgram.cs reads in place of the hardcoded http://localhost:6036/ fallback (Design Round 1, Q2) — reusing an existing mechanism rather than inventing a new one.
AC6 lands here because this is the task that actually exercises an AppHost restart against a running client: the script's discovery loop must re-resolve the gateway's port if the AppHost is restarted mid-session, proving the live-per-request resolution F-015-T02/T03 built survives the scenario end to end, not just in a unit test.
Depends on F-015-T05 — there must be a gateway resource in the AppHost for this script to discover.

## Closing note

Built on top of F-015-T05's `gateway` AppHost resource (the branch had drifted to a stale pre-Wave-1/2
snapshot mid-task; recovered by fast-forwarding onto `feat/F-015-api-gateway-and-mobile-contract`'s
current tip before making any changes).

- `scripts/run-ios.sh`: added `GATEWAY="Gateway"` alongside `SERVICES`; `wait_for_services` now also
  probes the gateway process with the existing `pid_of_service`/`http_port_of_pid` mechanism and only
  returns once both the seven services and the gateway answer `/health`, populating a new
  `GATEWAY_PORT` global the same way `PORTS` is already populated. `report_backend` prints the
  gateway's row. Before the simulator launch, the script exports
  `SIMCTL_CHILD_MAUI_API_BASE_URL="http://localhost:$GATEWAY_PORT/"` — `dotnet build -t:Run` does not
  call `xcrun simctl launch` directly in this script (the .NET iOS build tooling does that several
  process-levels down), so there is no `simctl launch` invocation to attach a flag to. Since Xcode 11,
  `simctl launch` reads any `SIMCTL_CHILD_`-prefixed variable off the *invoking* process's own
  environment, strips the prefix, and sets it in the launched app's environment — exporting it before
  `dotnet build -t:Run` means it is present for every descendant process in that build/launch chain,
  including whichever one ultimately calls `simctl launch`. The trailing NOTE block and the top-of-file
  comment were updated to describe the base-address fix accurately without overstating it (the
  `api/v1/` prefix problem is F-015-T07's, still outstanding).
- `MobileApp/Infrastructure/ApiBaseUrlResolver.cs` (new): `Resolve(IConfiguration, Func<string,string?>
  getEnvironmentVariable)` implements the priority chain `MAUI_API_BASE_URL` env var → `ApiBaseUrl`
  config → hardcoded `http://localhost:6036/` fallback. Not `#if MOBILE`-guarded — it compiles under
  the `net10.0` fallback TFM (`Microsoft.Extensions.Configuration.Abstractions` is already a transitive
  dependency of `Microsoft.Extensions.Http`, which `MobileApp.csproj` references unconditionally) so it
  is directly unit-testable, matching the `MobileApp/Routing/*` pattern from F-015-T06.
- `MobileApp/MauiProgram.cs`: both the `"AgendaBuddyApi"` and `"AgendaBuddyApiNoAuth"` named
  `HttpClient` registrations now call `ApiBaseUrlResolver.Resolve(builder.Configuration,
  Environment.GetEnvironmentVariable)` instead of inlining `builder.Configuration["ApiBaseUrl"] ??
  "http://localhost:6036/"`.
- `MobileApp.Tests/Infrastructure/ApiBaseUrlResolverTests.cs` (new): three tests pin the priority order
  — env var wins when set (regardless of config), config wins when the env var is unset, and the
  hardcoded default wins when neither is set. Uses `Moq` against `IConfiguration`, no environment
  mutation or Maui bootstrap needed.

Verification: `dotnet test MobileApp.Tests/MobileApp.Tests.csproj /p:MobileWorkloads=false` — 93 total,
86 passed, 7 skipped (pre-existing, unrelated to this task), 0 failed. `bash -n scripts/run-ios.sh`
passes. `dotnet build MobileApp/MobileApp.csproj -p:MobilePlatform=ios` was attempted to compile the
`#if MOBILE` half of `MauiProgram.cs` but fails in this environment before reaching that code — only
Xcode Command Line Tools are installed here, not full Xcode, and `xcrun simctl` is not present at all —
so the `MauiProgram.cs` MOBILE-gated edit and the `SIMCTL_CHILD_` env-var mechanism are verified by
static reading and documented Apple/Xcode 11+ `simctl` behavior only, not against a real booted
simulator. This should be re-verified against an actual simulator on a machine with full Xcode before
relying on it for a live demo.
