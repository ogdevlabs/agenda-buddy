LogoutAsync currently only clears local storage (AuthService.cs:78-83) — the server-side refresh token stays valid for its full 24-hour lifetime after a user logs out. Adds the POST api/v1/auth/logout call alongside the existing local clear.
Depends on F-015-T09 because logout and refresh share the same token lifecycle and are tested together most naturally — verifying "logout, then the old refresh token is rejected" needs the refresh call (T09) to exist as the thing being rejected.

**Closed 2026-08-23.** Added `AuthRouteBuilder.Logout()` (`MobileApp/Routing/AuthRouteBuilder.cs`) mirroring `Login()`/`Register()`/`Refresh()`. `AuthService.LogoutAsync` (`MobileApp/Services/AuthService.cs`) now `POST`s `api/v1/auth/logout` with the stored refresh token on the `AgendaBuddyApiNoAuth` client, wrapped in a `try`/`finally`: the local `jwt`/`refresh_token` clear always runs in `finally`, but a network exception is not caught — it propagates to the caller after the clear, matching this file's existing convention (`LoginAsync`/`RegisterAsync` never swallow a network failure either). If no refresh token is stored, the server call is skipped and only the local clear runs.

TDD: `MobileApp.Tests/Routing/AuthRouteBuilderTests.cs::Logout_BuildsPost` and three `MobileApp.Tests/Services/AuthServiceTests.cs` cases (`WithStoredRefreshToken_PostsToLogoutRouteAndClearsStorage`, `NoStoredRefreshToken_ClearsStorageWithoutCallingServer`, `ServerCallThrows_StillClearsStorage_AndPropagatesTheFailure`) were written first, watched fail (`AuthRouteBuilder.Logout` didn't exist), then made to pass. Mobile suite: 133 total (126 passed, 7 pre-existing skips) — baseline 130 + 3 new.

The "old refresh token is rejected on a subsequent refresh attempt" half of AC11 **was proven live**, not deferred: `AgendaBuddy.IntegrationTests/Harness/LogoutTest.cs` hosts a real Identity service (`ServiceHostFixture<IdentityAnchor>`) and, via `MobileApp.Routing.AuthRouteBuilder`'s own `Logout()`/`Refresh()` specs, seeds a credential with a known refresh-token hash (`IdentityService.HashToken`, bypassing `POST /register`/`/login` — those need `JWT_PRIVATE_KEY`, which `CryptoSessionFixture` deliberately never materialises as a string per F-016 AC-3), calls `POST /api/v1/auth/logout` with the raw token, confirms the credential's embedded `refresh_token` sub-document is `$unset`, then calls `POST /api/v1/auth/refresh` with the same token and asserts `401 Unauthorized`. A second, independent-credential control test (`Refresh_WithAValidUnexpiredToken_MatchesTheCredential`) proves the same seed shape is matched (500 — the missing-signing-key path, reached only after a successful lookup, since this harness never sets `JWT_PRIVATE_KEY`) when *not* logged out first — establishing that the 401 is a real transition, not a token that was never live. A third test pins logout's idempotency (an unrecognized token still gets 204). Integration suite: 212 total, all passing — baseline 209 + 3 new.

One implementation pitfall worth recording: an early version of the main test called `/refresh` *before* logout as a "still valid" baseline — but `IdentityService.RefreshAsync` rotates the stored hash on every matched attempt, even on the path that goes on to fail differently (missing signing key), so that call silently invalidated the test's own token. Fixed by asserting "previously valid" directly against the seeded MongoDB document instead (matching the exact fields `RefreshAsync`'s filter checks), and moving the "matched-but-unsigned-key returns 500" proof into the separate control test with its own disposable token.
