Deletes SeedDataProvider and every fallback call to it (DashboardViewModel.LoadAsync, CalendarViewModel's equivalent). Fixes the two bugs the fallback was hiding: ErrorMessage is currently hardcoded to string.Empty and never reassigned (HasError can never be true); a zero-length result is currently replaced by seed data before being assigned (IsEmpty can never be true). Both become reachable the moment the interception is removed — this task is what actually exercises them for the first time since F-012 shipped.
Depends on F-015-T07: the error banner and empty state are meaningless to wire until the calls feeding them return real 2xx/error responses instead of a 404 that always looked like "no data, use seed."

**Closed 2026-08-23.** `MobileApp/Services/SeedDataProvider.cs` is deleted. Five ViewModels carried the
seed-fallback pattern — `DashboardViewModel`, `CalendarViewModel`, `CustomersViewModel` (local
`SeedContacts()`, not `SeedDataProvider`, but the identical shape), `MessagingViewModel`, and
`NotificationsViewModel` — all fixed the same way: `LoadAsync` now assigns the service result directly
(a genuine zero-length success stays zero-length, making `IsEmpty` reachable for the first time) and the
`catch` block, widened from `HttpRequestException` to `Exception` (matching `MessagingViewModel`'s
pre-existing convention and covering `JsonException`/`TaskCanceledException`/`AmbiguousWriteException`
from F-015-T09's handler), sets a real `ErrorMessage` instead of generating seed data — making `HasError`
reachable for the first time. `AppointmentDetailViewModel` and `MessageThreadViewModel` never called
`SeedDataProvider` and were already doing this correctly; left untouched.

Verified with new/rewritten ViewModel tests (`MobileApp.Tests/ViewModels/*Tests.cs`) mocking each
`*ApiService` to throw (asserts `HasError` true, a non-empty real `ErrorMessage`, and no fabricated items)
and to return an empty success list (asserts `IsEmpty` true, zero items, no fabricated items), plus a new
`SeedDataProviderRemovalTests.cs` proving via reflection that the type no longer exists in the `MobileApp`
assembly at all — the strongest available guarantee that no ViewModel (or anything else) can reach it.
Full mobile suite: 133 tests (126 passed, 7 skipped — the 7 pre-existing `AuthAcceptanceTests` skips,
unrelated), up from a 130 baseline: net +3 (one added Calendar empty-result case, two in the new removal
test file); no regressions.

**Deviation / open question for follow-up:** two comments left by F-015-T07 in `NotificationApiService.cs`
and `MessagingApiService.cs` assign additional, related work to this task — (1) `MessageThreadViewModel`
passes `ThreadId` (an opaque, fabricated id) to `GetThreadAsync` where the real route keys on the
counterpart's email (`RecipientEmail` is already threaded through via the page's query property but never
used for the load call), and (2) `NotificationsViewModel.MarkReadAsync` treats a `null` result as failure,
but the real route now answers `204 No Content` on genuine success, which `NotificationApiService`
currently also surfaces as `null` — collapsing "worked" and "failed" into the same signal. Neither is
SeedDataProvider-shaped (no fabricated data is involved) and neither is covered by AC1 or AC8, so both are
left as-is here rather than risking scope creep against tests pinned to the current (T07) contract
(`MessageThreadViewModelTests.SendAsync_ValidBody_CallsServiceAndAppendsMessage` asserts
`GetThreadAsync("t1", …)`, and `NotificationsViewModelTests.MarkReadAsync_ServiceReturnsNull_...`
asserts null-means-unchanged). Recommend filing both as separate follow-up issues.
