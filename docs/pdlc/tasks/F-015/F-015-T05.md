Adds the eighth resource to AppHostWiring.cs following the AddApi<TProject> helper pattern already used for all seven services: `builder.AddProject<Projects.Gateway>("gateway", launchProfileName: null)`, then `WithReference`/`WaitFor` on all seven, matching how the AppHost already composes MongoDB and Kafka. `WithReference` is what injects the `services__<name>__http__0` keys F-015-T03 reads; `WaitFor` on all seven means the gateway only reports healthy once every destination it could route to is also healthy.
No PRD acceptance criterion of its own — this is AppHost composition, not routing behavior. **Correction made during Build (wave-order fix):** the Plan originally assigned AC3/AC4 (JWT passthrough proof) to this task, reasoning it was "the first point a full request can flow end to end" — but that's wrong: this task only adds the resource and its references, with no route table yet (F-015-T03, Wave 3) to actually forward anything through. AC3/AC4 cannot be verified without a working route, so they are reassigned to F-015-T04, which already depends on T03 and is where "prove things work through the gateway to a real backend" belongs. Recorded here rather than silently moved, per the Readiness Assessment's own flagged wave-order risk.
New AppHost model tests, mirroring the existing AppHostWiringTest pattern, asserting the resource exists with the correct references/waits — not the end-to-end auth behavior, which moved to T04.

**Build note:** Started from a stale branch point (Inception commit `227acbf`, before Wave 1 — T01/T06/T13 — merged into `feat/F-015-api-gateway-and-mobile-contract`); fast-forwarded onto the branch tip (`8504c71`) first to pick up F-015-T01's Gateway scaffold, the hard dependency for this task.

Added three tests to `AppHostWiringTest.cs` (TDD red first — they failed with "the collection was empty" against the unmodified model, confirming no `gateway` resource existed yet): `GatewayIsRegistered` (asserts a `ProjectResource` named `gateway` exists), and two `[Theory]`s over the seven service names — `GatewayReferencesEveryService` and `GatewayWaitsForEveryService` — asserting each service name appears in the gateway's `WithReference`/`WaitFor` relationship annotations, mirroring the existing `KafkaIsReferencedBy`/`EveryServiceWaitsForMongoDb` pattern.

Implementation in `AgendaBuddy.AppHost/AppHostWiring.cs`: the `AddApi<TProject>` local function was `void`, so the seven service builders had no captured local variables to reference. Changed its return type to `IResourceBuilder<ProjectResource>`, added `return service;`, and captured each of the seven `AddApi` calls into a named local (`identity`, `booking`, `customer`, `provider`, `calendar`, `services`, `profession`). Then added `builder.AddProject<Projects.Gateway>("gateway", launchProfileName: null)` as the eighth resource, followed by a `foreach` over the seven captured builders calling `.WithReference(service)` and `.WaitFor(service)` on each — exactly the shape specified in this task's body. Also added `<ProjectReference Include="..\Gateway\Gateway.csproj" />` to `AgendaBuddy.AppHost.csproj`, which was missing and is required for the Aspire AppHost SDK to source-generate `Projects.Gateway`.
