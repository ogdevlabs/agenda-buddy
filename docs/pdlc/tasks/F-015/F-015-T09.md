AuthService already stores and clears a refresh token but has never called POST api/v1/auth/refresh — this task wires that call into JwtDelegatingHandler's 401 path, retrying the triggering request once with the new token rather than immediately purging and bouncing to login. Distinct from the existing reactive-logout path, which stays as the fallback when refresh itself fails or the refresh token is rejected (single-use per F-021 — a second device or a race gets exactly one success).
Separately, and independent of the refresh path: any write request (note, payment, message, status transition) that times out ambiguously at the gateway hop must not be auto-retried — the client surfaces "unknown result, check before retrying" instead. This is the conservative mitigation Discovery chose over idempotency keys (out of scope, filed as a follow-up).
Depends on F-015-T06 (testable structure) and F-015-T05 (a real gateway+backend to exercise the 401→refresh→retry sequence against).

**Closed 2026-08-23.** `JwtDelegatingHandler` now takes `IHttpClientFactory` alongside `ISecureStorageService`. On a 401 it clones the triggering `HttpRequestMessage` up front (via a new `HttpRequestMessageExtensions.CloneAsync`, since a request can only be sent once), calls `POST api/v1/auth/refresh` on the `"AgendaBuddyApiNoAuth"` client with the stored refresh token (new `AuthRouteBuilder.Refresh()`), and on success retries the cloned request once with the new access token — the caller sees the retried response, not the 401. `TryRefreshTokenAsync` returns the new access token directly rather than round-tripping through secure storage again, so the retry never depends on a second `GetAsync` returning something different from the first. Refresh failure (network error, malformed response, or a rejected/expired/already-consumed refresh token per F-021 single-use semantics) falls back unchanged to the existing purge + `UnauthorizedAccess` event.
Independently, non-idempotent writes (`POST`, and every `PUT` — no per-request idempotency metadata exists to prove any `PUT` safe, so all are treated conservatively as writes, matching the status-transition example in the ACs) that time out (an HttpClient-level `TaskCanceledException` whose token is not the caller's own) or come back `502`/`504` now throw a new `AmbiguousWriteException` instead of returning a response — the client never auto-resubmits. Reads and the refresh-retry itself are unaffected: retrying after a resolved 401 is safe regardless of method, since the retry's cause (a stale token) is known, unlike a gateway-hop timeout where the write's fate is unknown.
9 new tests added to `MobileApp.Tests/Infrastructure/JwtDelegatingHandlerTests.cs` (2 → 11), covering both ACs plus the negative cases (GET timeout/502 do not throw the ambiguous-write type). Full mobile suite: 90 → 99 tests, 0 regressions (83→92 passing, 7 skipped throughout).
