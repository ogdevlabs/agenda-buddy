AuthService already stores and clears a refresh token but has never called POST api/v1/auth/refresh — this task wires that call into JwtDelegatingHandler's 401 path, retrying the triggering request once with the new token rather than immediately purging and bouncing to login. Distinct from the existing reactive-logout path, which stays as the fallback when refresh itself fails or the refresh token is rejected (single-use per F-021 — a second device or a race gets exactly one success).
Separately, and independent of the refresh path: any write request (note, payment, message, status transition) that times out ambiguously at the gateway hop must not be auto-retried — the client surfaces "unknown result, check before retrying" instead. This is the conservative mitigation Discovery chose over idempotency keys (out of scope, filed as a follow-up).
Depends on F-015-T06 (testable structure) and F-015-T05 (a real gateway+backend to exercise the 401→refresh→retry sequence against).
