The tested TFM (net10.0 fallback) has no DI registration and no Shell at all — MauiProgram.cs and AppShell.xaml.cs are wrapped in #if MOBILE — so every wiring defect this feature fixes would otherwise stay untestable under CI, the same shape of gap F-016 closed for endpoint authz.
Extracts each *ApiService's route-string construction (which path, which verb, which query params) into a plain class with no Maui or DI dependency, constructible directly in a unit test. This is the "narrow the untestable surface" approach F-016 used splitting DockerPreflight's probe from its diagnose logic (Design Round 3, Q3) — not a fake IServiceProvider that fights the #if MOBILE boundary.
No dependency on the gateway existing yet — this is a pure refactor of existing route strings, testable in isolation before F-015-T07 corrects what those strings actually say.

**Closed 2026-08-23.** Extracted route-building logic from all six `*ApiService` classes into six new plain, Maui-free, DI-free static classes under `MobileApp/Routing/` (net10.0-only, no `#if MOBILE`, constructible directly in `MobileApp.Tests`):
- `MobileApp/Routing/RouteSpec.cs` — a `readonly record struct RouteSpec(HttpMethod Method, string Path)` shared by every builder, so both the path/query-string decision and the HTTP-verb decision are one directly-assertable value.
- `MobileApp/Routing/BookingRouteBuilder.cs` — `TodayAppointments(DateOnly)`, `Appointment(string id)`, `UpdateAppointmentStatus(string id)`, `BuildUpdateStatusPayload(AppointmentStatus)` (the `{ "status": "<name>" }` body shape).
- `MobileApp/Routing/CalendarRouteBuilder.cs` — `Availability(DateOnly from, int days)`.
- `MobileApp/Routing/CustomerRouteBuilder.cs` — `Customers()`.
- `MobileApp/Routing/MessagingRouteBuilder.cs` — `Inbox()`, `Thread(string threadId)`, `SendMessage()`, `BuildSendMessagePayload(string recipientEmail, string body)`, `MarkRead(string id)`.
- `MobileApp/Routing/NotificationRouteBuilder.cs` — `Notifications()`, `MarkRead(string id)`.
- `MobileApp/Routing/AuthRouteBuilder.cs` — `Login()`, `Register()` (already-correct routes, extracted anyway per the task brief so F-015-T09/T10's refresh/logout wiring gets the same testable pattern).

`BookingApiService`, `CalendarApiService`, `CustomerApiService`, `MessagingApiService`, `NotificationApiService`, and `AuthService` now call into these builders for the path (and, for Booking's status update and Messaging's send-message, the request body) instead of interpolating strings inline. `HttpClient` dispatch — which named client, which verb-specific method (`GetAsync`/`PutAsync`/`PostAsync`/`PatchAsync`/`PostAsJsonAsync`), response-status handling and deserialization — was left exactly as it was, per the task's instruction to keep HTTP-calling logic in the `*ApiService` classes.

TDD was followed literally: 16 new tests (`MobileApp.Tests/Routing/{Booking,Calendar,Customer,Messaging,Notification,Auth}RouteBuilderTests.cs`) were written and confirmed **red** (`CS0234`, the `Routing` namespace did not exist) before any of the six production classes were created; creating them turned all 16 green with no other change. Each test pins the *current* (pre-F-015-T07) route/verb/body — including the known-wrong ones (`booking?date=...` with no `api/v1/` prefix, `calendar?from=...&days=...`, bare `customer`/`messages`/`notifications`) — by design, since correcting them is F-015-T07's job against these same classes.

No deviations from the suggested shape were needed beyond adding the shared `RouteSpec` type (to make the verb decision, not just the path, independently assertable) and `Build*Payload` helper methods for the two operations (`BookingApiService.UpdateStatusAsync`, `MessagingApiService.SendMessageAsync`) that decide a request body shape, not just a path. `PushNotificationService.PostTokenAsync`'s `"device-token"` route was left untouched — it is not one of the `*ApiService` classes this task names, and the task brief did not ask for it.

Mobile suite: **74 → 90 tests** (67 → 83 passing, 7 skipped throughout — unchanged). `dotnet test MobileApp.Tests/MobileApp.Tests.csproj /p:MobileWorkloads=false` is green. Files touched: 7 new files under `MobileApp/Routing/`, 6 new test files under `MobileApp.Tests/Routing/`, and edits to the 6 `*ApiService`/`AuthService` files listed above.
