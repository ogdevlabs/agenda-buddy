Two things, because both are about what crosses the gateway boundary unmodified: an error handler that attaches the failed destination's YARP cluster name to a ProblemDetails body on 5xx/timeout/unreachable (api-contracts.md §1) — this is the single point of translation PRD AC 5 needs, so MobileApp never has to guess which service failed from the route it called; and an explicit assertion (threat T-303) that YARP's default X-Forwarded-* header forwarding does not break any backend's UseAgendaBuddyTransportSecurity() → UseAuthentication() ordering or its HSTS/redirect behavior when reached through the gateway instead of directly.
Depends on F-015-T03 (the failure-translation handler needs the route/cluster table to exist first — it names clusters that table defines) and F-015-T05 (needs the gateway wired into the real AppHost graph to test against real services, not stubs).
**Reassigned during Build (wave-order fix):** AC3 and AC4 (JWT-passthrough proof) moved here from F-015-T05, which the Plan had assigned them to on the mistaken assumption that AppHost wiring alone makes a full request flow provable — it doesn't, without T03's route table. This task is the first point a full client→gateway→destination request can actually be exercised, so the auth-passthrough proof belongs here.

**Closed 2026-08-23.** All four ACs built and proved over real HTTP (in the `TestServer` sense the rest of this harness already uses — see `ServiceHostFixture`'s own class remarks on what "real HTTP" means here); `AgendaBuddy.IntegrationTests` went from 209 to 227 (18 new tests), zero regressions, backend `agenda-buddy-backend.slnf` suites all green too.

- **AC5 (failure translation).** `Gateway/Program.cs` registers a global YARP response transform (`AddTransforms(...).AddResponseTransform(TranslateDestinationFailureAsync)`) rather than middleware wrapped around `MapReverseProxy` or a custom `IErrorHandler` — response transforms are YARP 2.3's documented hook that runs *before* any bytes reach the client (default header/status copy happens first, then transforms, then the body-copy decision), so overwriting the status/body is safe even for a destination that DID respond with its own 5xx (not just the null-`ProxyResponse` connection-refused/timeout case). Reads the failed cluster id off `HttpContext.GetReverseProxyFeature().Cluster`, sets `SuppressResponseBody`, clears any headers the default copy already applied, and writes the `api-contracts.md` §1 `gateway-destination-unreachable` ProblemDetails body via the same `Results.Problem(...).ExecuteAsync(...)` pattern T03's `HandleNoRoute` already used. Proved in `AgendaBuddy.IntegrationTests/Harness/GatewayFailureTranslationTest.cs` (9 tests) against closed loopback ports per the task's own guidance — no live AppHost or stopped service needed.
- **AC3/AC4 (JWT passthrough).** `AgendaBuddy.IntegrationTests/Harness/GatewayJwtPassthroughTest.cs` (6 tests) routes real requests through a real `Program.cs` Gateway pipeline to a real Booking service (`ServiceHostFixture<BookingAnchor>`, same MongoDB-backed pipeline `PaymentsAndStatusTest` exercises directly), using `TokenFactory` for valid/expired/tampered/anonymous tokens. A valid JWT transitions the appointment exactly as a direct call would (200, DB updated); a valid JWT for the wrong role or the wrong subject gets the same 403 Booking's own ownership/role checks would give directly; anonymous, expired, and tampered tokens all get the same 401 `PaymentsAndStatusTest.AC8` proves for a direct call. Enabled without a real TCP socket by a new `AgendaBuddy.IntegrationTests/Harness/GatewayToRealServiceHarness.cs`: a custom `IForwarderHttpClientFactory` hands YARP the target backend's own `TestServer.CreateHandler()` for the one cluster under test, so the request still crosses YARP's real routing/transform/failure-translation code, just over the same in-memory transport the rest of this harness already relies on. `ServiceHostFixture.cs`/`ServiceHost` gained a `Server` property (the `TestServer` behind `Client`) to make this possible.
- **T-303 (`[security]`, test-first).** `AgendaBuddy.IntegrationTests/Harness/GatewayTransportSecurityParityTest.cs`, exact name `T303_GatewayForwardedRequest_TransportSecurityBehaviorMatchesDirectCall` (plus a same-class `T303_WithTheDefaultConfiguration_NeitherPathSendsHsts`). Passed on first run with **no production code change** — confirmed non-vacuous by mutation rather than a natural red/green pair: temporarily adding `app.UseForwardedHeaders(...)` to Profession's pipeline (simulating exactly what T-303 warns against) turned the `scheme: "http"` case red, because the backend then trusted the client's forwarded scheme instead of the scheme it actually received the request on; reverted immediately, confirmed clean (`git diff` empty) before committing. Finding: neither Gateway nor any of the seven backends calls `UseForwardedHeaders()`, so YARP's default `X-Forwarded-*` forwarding is present but inert as far as `UseAgendaBuddyTransportSecurity()` is concerned — HSTS/redirect behavior depends only on the scheme/host the backend itself actually received (i.e. the destination address YARP dialed), which is provably identical to a direct call at the same scheme. `UseHttpsRedirection()` stays a no-op on both paths in this project's current topology (no service in `AppHostWiring.cs` has an HTTPS endpoint), so "no redirect loop" holds today by construction, not by this task's mitigation — this test is what stops that continuing to be assumed if that topology ever changes.

**Open items / deviations, none blocking:**
- `IForwarderErrorFeature`'s `Exception`/specific `ForwarderError` value is not surfaced in the ProblemDetails body — `detail`/`failedService` name which cluster failed, not why, matching what `api-contracts.md` §1 actually specifies. If MobileApp's error UI ever wants to distinguish "timed out" from "connection refused", that detail is available (`HttpContext.GetForwarderErrorFeature()`) but wasn't asked for here.
- A destination that connects and returns its own 5xx (as opposed to failing to connect) is folded into the same `gateway-destination-unreachable` shape rather than a distinct one — `api-contracts.md` §1 groups them together ("unreachable, timed out, or 5xx") and MobileApp's error-display logic (PRD AC5) doesn't need to tell them apart, so this wasn't split further.
- Noted in passing, not this task's scope: `Identity/Extensions/RateLimitingExtensions.cs` already flags that `TestServer` (and a real deployment behind a proxy that doesn't forward the client address) leaves `RemoteIpAddress` null, and names `UseForwardedHeaders()` as F-017's future fix for that. T-303's finding here — that no service calls it yet — is the same fact from the transport-security side; F-017, whenever it lands, should re-run `GatewayTransportSecurityParityTest` since adding `UseForwardedHeaders()` for the rate-limiting IP fix would also change what this task just proved.
