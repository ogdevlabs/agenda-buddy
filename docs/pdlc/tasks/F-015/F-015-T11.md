## Closed 2026-08-23

**Deviation, recorded rather than silently followed.** The task brief and `ux-review.md`'s own triage
("no new screen, no new component; this feature wires existing screens to real data") both assumed a
report screen and a payment screen already existed in `MobileApp` for this task to attach copy to.
They did not: `IProviderApiService.GetReportAsync` and `IBookingApiService.GetPaymentAsync` (wired by
F-015-T07) had no ViewModel, Page, route, or DI registration consuming them anywhere in the client —
confirmed by exhaustive search, not an oversight in locating them. Meeting AC13's literal text ("the
report screen renders…", "the payment screen's copy…") required building the minimal screens: new
`ProviderReportViewModel`/`ProviderReportPage` (reachable from Dashboard via a provider-only "Your
Report" button) and `PaymentViewModel`/`PaymentPage` (reachable from `AppointmentDetailPage` via a new
"Payment" card), both registered in `MauiProgram.cs` and routed via `Routing.RegisterRoute` in
`AppShell.xaml.cs` (matching the existing `messageThread`/`appointmentDetail` pushed-route pattern, not
top-level `ShellContent`).

**Copy placed, verbatim:**
- Report (`ProviderReportViewModel.RevenueMessage`, bound in `ProviderReportPage.xaml`): *"Revenue
  isn't available yet — [reason]."* when `RevenueAvailable` is `false`. The real server-side reason
  (`Library/Services/ReportingService.RevenueUnavailable`) already ends with a period, so the message
  trims it before appending one — the naive concatenation the ux-review's formula implies would have
  doubled it. Never a number: `ProviderReport` has no revenue amount field at all today (F-014 removed
  the only one that existed), so the `RevenueAvailable: true` branch has no real figure to render yet
  either.
- Payment (`PaymentViewModel.StatusMessage`, bound in `PaymentPage.xaml`): *"Payment recorded (not yet
  charged)"* whenever `PaymentEntity.StripePaymentIntentId` starts with `local_`
  (`PaymentViewModel.IsNonCharging`), regardless of `PaymentStatus` — never "Paid" for a non-charging
  payment (ADR-038). A real Stripe intent still maps `Succeeded` → "Paid".
- Notifications empty state (`NotificationsViewModel.EmptyStateMessage`, bound in
  `NotificationsPage.xaml`, replacing the old "No Notifications" / "You're all caught up." pair):
  *"No notifications yet — you'll see updates about your appointments here."*

**Error banner mapping (finding 2).** New `MobileApp/Infrastructure/GatewayErrorMapper.Describe(string?
failedService)`: `booking`→"Booking", `calendar`→"Calendar", `customer`→"Customers",
`provider`→"Providers", `services`→"Services", `profession`→"Professions", `identity`→"Account",
rendering `"[Name] is unavailable right now. Try again."`; `null`/empty/unrecognized falls back to a
generic connectivity message. Wired end-to-end (not just unit-tested in isolation): new
`GatewayServiceUnavailableException` + `HttpResponseMessageExtensions.TryReadFailedServiceAsync`
(best-effort ProblemDetails parse, `api-contracts.md` §1) are thrown from
`BookingApiService.UpdateStatusAsync`/`GetPaymentAsync` and `ProviderApiService.GetReportAsync` only
when a `failedService` field is actually present on a non-success response — an ordinary domain 4xx
with no such field still returns `null` exactly as before, so no existing failure-path test changed
behavior. `AppointmentDetailViewModel`, `ProviderReportViewModel`, and `PaymentViewModel` each catch it
and render the mapped message.

**Loading state (finding 4 / 8-state spot-check).** `AppointmentDetailViewModel` gained `IsCompleting`,
set only around the `Completed` transition (not Confirm/Cancel) in `ExecuteStatusUpdateAsync`, plus two
derived properties (`ShowCompleteButtonIdle`, `ShowCompletingIndicator`) so the Complete button is
replaced by an `ActivityIndicator` while the call is in flight — the same Button+ActivityIndicator
overlay-in-a-Grid pattern `LoginPage.xaml` already uses for its Sign In button, not a new pattern.

**TDD (AC13).** Failing-first tests added: `ProviderReportViewModelTests` (exact revenue copy, never a
number/blank), `PaymentViewModelTests` (exact non-charging copy, never "Paid"),
`NotificationsViewModelTests.LoadAsync_EmptyResult_RendersExactEmptyStateCopy`,
`GatewayErrorMapperTests` (all seven cluster ids + case-insensitivity + null/empty/unknown fallback),
plus `AppointmentDetailViewModelTests` busy-flag tests using a `TaskCompletionSource<AppointmentDetail?>`
to observe `IsCompleting`/`ShowCompletingIndicator`/`ShowCompleteButtonIdle` true mid-flight and false
after resolution. Also added: `BookingApiServiceTests`/`ProviderApiServiceTests` coverage for the new
`GatewayServiceUnavailableException` throw path.
