ADR D-2: two NEW TOP-LEVEL route groups in the Customer process, not children of /api/v1/customers. A message is addressed to a PERSON — a provider has an inbox for the same reason a customer does — so a URL saying `customers` about a provider's inbox asserts something false that every client then works around. Identity already hosts two unrelated groups, so this is precedent, not novelty.
Threat T-204: the inbox takes NO recipient parameter, and the thread route takes ONE counterpart with the other side always the caller's claim. MessageService derives thread_id by sorting both addresses, so a thread between two other people has no representation in the URL space at all — unrequestable rather than merely refused.
Threat T-208: there is deliberately no route that CREATES a notification. One would let any caller write a convincing "Your appointment was cancelled" into somebody else's list. The consequence is that the list is empty until a domain event writes one, and nothing does yet — asserted as an expectation so an empty GET is not read as a bug.
Every scoping test plants a THIRD party's records in the same database, because a route returning nothing would satisfy "only your own" vacuously.
