The part of F-014 that is not wiring, and it is here because ReportingService is meaningless without it (Discover F-1): its two headline numbers come from AppointmentStatus, and nothing in production ever set anything but Requested.
Book() and Complete() held the transition rules and were NEVER CALLED outside tests. What ran was UpdateAppointmentCommandHandler:51 copying the client's value — so a customer could mark a brand-new appointment Completed, asserting work was delivered. MobileApp already drives status this way (AppointmentDetailPage.xaml.cs:93), so the design was live; only F-015's absence kept it harmless.
Now: the PUT ignores the field entirely, and a dedicated route applies the transition THROUGH THE ENTITY (ADR D-4), so a state added to the enum without a method is unreachable by construction. Illegal transitions answer 409 — the request is well-formed, it conflicts with the state.
Both stored copies are written, and that is not redundancy: ReportingService counts from the EMBEDDED list, so updating only the collection would leave the dashboard reporting the old status indefinitely. The two writes are not atomic together (separate documents, no replica set, no transaction) and that is recorded in the handler rather than hidden.
AND the cancellation inversion is fixed in the same task (Discover F-3): CancelAppointmentCommandHandler refused a BOOKED appointment — the state a customer actually needs to cancel. Invisible while nothing set Booked; making transitions real activates it, so shipping them separately would have looked like the status fix broke cancellation.
Found while testing: the API binds enums as INTEGERS (no JsonStringEnumConverter anywhere), so a string `"Completed"` fails model binding with a bare 400. The new route takes a string deliberately and parses it, with Enum.IsDefined to reject undefined numerics — TryParse accepts "99" and returns 99.
