NOT PLANNED. Found by running the first notes test, which failed on `Assert.NotEqual(ObjectId.Empty, note.Id)`.
System.Text.Json has no idea what an ObjectId is, so it serialised the struct's public properties and emitted `"id": { "timestamp": …, "machine": …, "pid": … }` — a shape that cannot be deserialised back into an ObjectId at all, because it has no settable properties. Three of F-014's route families need the id from a create response to function: PUT /notes/{id}, POST /messages/{id}/read, POST /notifications/{id}/read.
PRE-EXISTING, not introduced here: every route returning ProviderEntity, CustomerEntity, ServiceEntity or ProfessionEntity has emitted the same unusable id since it was written. Nothing noticed because the mobile client cannot reach them (F-015) and no test read an id back.
Registered in the three services F-014 touches, because its own routes cannot work without it. The other four are FILED rather than changed — altering their response shape is not this feature's business.
Carried to F-015: a client needs the same converter, or entities should declare `string Id` with [BsonRepresentation(BsonType.ObjectId)] as CredentialEntity already does, which needs no converter on either side.
