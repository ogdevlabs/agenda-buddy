Carved out of T-10 (build-loop step 9e split): five acceptance criteria need the AppHost to actually provision MongoDB and Kafka, and the build machine had no container runtime (neither docker nor podman installed). Everything else in T-10 was verified and recorded in docs/pdlc/design/aspire-wiring/verification.md. Requires: a machine with Docker Desktop or Podman running. Steps: (1) clean shell, no exported env vars, run 'dotnet run --project AgendaBuddy.AppHost'; paste the two JWT keys at the prompt. (2) AC-1.1 starts successfully. (3) AC-1.2 dashboard lists 9 resources. (4) AC-1.3 all 7 services Healthy. (5) AC-2.3 every service resolves its connection string under the AppHost. (6) AC-3.4 traces, metrics and structured logs appear for all 7. (7) Threat T-004: inspect exported spans and confirm they carry http.route templates, not raw paths containing an email address. Record the outcome in verification.md and the episode.

## Attempt 1 (2026-08-17, Rancher Desktop available) — PARTIAL, still open

Container runtime became available mid-session (Rancher Desktop, docker 29.5.3 at `~/.rd/bin/docker` — **not on PATH by default**; the VM has 2 CPUs / 4.1 GB and is already running a k8s cluster).

**Verified:**
- **AC-1.1 (partial)** — `dotnet run --project AgendaBuddy.AppHost` starts in a shell with **no exported environment variables**. The JWT keys came from user secrets (`Parameters:jwt-public-key` / `:jwt-private-key`), which is exactly the documented first-run flow. Dashboard came up on a dynamic port.
- **Infrastructure half of AC-1.2** — both containers started and stayed healthy on the constrained VM: `mongo:8.3` (published `127.0.0.1:32770`) and `confluentinc/confluent-local:8.2.0`. Mongo logged normal WiredTiger checkpoints; Kafka's `QuorumController` was serving. The `1/1 brokers are down` errors in the log are transient rdkafka startup probes, not our services.

**NOT verified — the seven services never started.** DCP created only 1 executable (the dashboard) and 0 executablereplicasets, while registering 20 `services` and 6 `endpoints`. So Aspire knows the projects' network definitions but never asked DCP to run them. No error appears in the AppHost log.

**Ruled out by experiment** (both reverted afterwards; `AppHostWiring.cs` is unchanged from its committed state):
1. Clearing `EndpointAnnotation.TargetPort` — re-ran clearing only `Port`; still 0 executables.
2. `WaitFor(mongo)` / `WaitFor(kafka)` gating — re-ran with both removed; still 0 executables.

**Leading hypothesis: the ASP.NET Core / Aspire development certificate is not trusted.** Two warnings were present on every run:
- `Aspire.Hosting.Dcp.DcpHost: No trusted Aspire development certificate was found. See https://aka.ms/aspire/devcerts`
- `Microsoft.AspNetCore.Server.Kestrel.Core.KestrelServer: The ASP.NET Core developer certificate is not trusted.`

This machine's .NET install printed "To trust the certificate, run `dotnet dev-certs https --trust`" on first use and it was never run. Trusting requires an **interactive keychain authorisation**, which an agent cannot perform.

**Next steps for whoever picks this up:**
1. Run `dotnet dev-certs https --trust` (accept the keychain prompt), then `dotnet dev-certs https --check --trust` to confirm.
2. Put Rancher's CLI on PATH for the session: `export PATH="$HOME/.rd/bin:$PATH"` — Aspire shells out to `docker`.
3. Consider raising the Rancher VM allocation; 2 CPUs / 4 GB already running k8s is tight for Mongo + Kafka + 7 services.
4. Re-run `dotnet run --project AgendaBuddy.AppHost` and complete AC-1.2 (9 resources listed), AC-1.3 (all 7 Healthy), AC-2.3 (each service resolves its connection string), AC-3.4 (traces/metrics/logs), and threat T-004 (exported spans carry `http.route` templates, not raw paths containing an email). Also close review finding A-3 — observe that JWT masking survives into the dashboard.
5. If the services still do not start with a trusted cert, the next suspects are `launchProfileName: null` (try omitting it and instead clearing ports only) and the AppHost↔project reference metadata.

**Assessment:** not a proven defect in the wiring — the model is asserted by 28 tests, and all 7 services start correctly outside the AppHost in both `Development` and `Staging`. But **AC-1.1 and AC-1.3 remain unproven end-to-end**, and this task stays open.

## Attempt 2 (2026-08-17, dev cert trusted) — ROOT CAUSE BISECTED, fix not yet applied

`dotnet dev-certs https --trust` was run. **The dev-certificate hypothesis from attempt 1 is disproven** — still 0 service executables with a trusted cert.

### Established by side-by-side experiment

A minimal throwaway AppHost (`/tmp/aspire-probe`) launched its project fine, proving Aspire project launching works in this environment and the fault is in **our wiring**. Then, in our own graph, one service was added twice — once with the generic overload and once with the string-path overload:

| How the project was added | DCP executable created? |
|---|---|
| `AddProject<Projects.Booking>("booking", launchProfileName: null)` | ❌ no |
| `AddProject("booking-via-path", "../Booking/Booking.csproj")` | ✅ **yes** |

**Blocker 1 — the generic `AddProject<TProject>` overload creates no executable.** It resolves SDK-generated metadata (`obj/Debug/net10.0/Aspire/references/*.ProjectMetadata.g.cs`) whose `SuppressBuild` is `true`. The path is correct and the file exists, yet DCP never gets an executable and **nothing is logged**. Aspire registers the DCP `services` and `endpoints` for all seven, so the graph is built — only the launch never happens.

**Blocker 2 — at least one of three additions also blocks launch.** With the path overload, all 7 services launched **only** in this configuration:

```
AddProject(name, projectPath).WithReference(database)      // ← 7/7 launched
```

Adding these back (all three present) returns to 0 executables:
- the `foreach (… EndpointAnnotation) { Port = null; TargetPort = null; }` loop (AC-1.4)
- `.WaitFor(mongo)` / `.WaitFor(kafka)` (E-6)
- `.WithEnvironment("JWT_PUBLIC_KEY", jwtPublicKey)` with a **`ParameterResource`** (T-003)

A single-line parameter value fails the same way, so the multi-line PEM is **not** the cause.

> ⚠️ **The attempt-1 "ruled out" list was invalid.** Those experiments each removed one feature while still using the generic overload — which was independently broken — so they proved nothing. Do not trust them; blocker 2 has not been narrowed to a single cause yet.

### Known-good baseline to bisect from

```
7/7 launch:  AddProject(name, path).WithReference(db)     — no port clearing, no WaitFor, no parameter env
0/7 launch:  the same + all three of the above
```

Add back **one at a time**, ~3 minutes per run:
1. `+ WaitFor(mongo)` — most likely benign; if it blocks, the Mongo health check is not going healthy.
2. `+ port clearing` — if it blocks, AC-1.4 needs a different mechanism than mutating Aspire's annotations. Try `WithHttpEndpoint`/`WithEndpoint(name, callback)` instead of post-hoc mutation, or removing the Kestrel-derived annotations rather than nulling their ports.
3. `+ parameter-backed WithEnvironment` — if it blocks, the fallback is a plain string (`builder.Configuration["Parameters:jwt-public-key"]`), which **loses dashboard masking and weakens the T-003 mitigation** — surface that tradeoff rather than taking it silently.

### Repo state

`AppHostWiring.cs` is **reverted to its committed state** — every experiment above was undone. 286 tests still pass. The fix is *not* applied: the committed AppHost still uses the generic overload and therefore still will not launch the services.

**AC-1.1, AC-1.2, AC-1.3, AC-2.3, AC-3.4 remain unverified. T-014 stays open**, but is now a ~15-minute bisection rather than an open-ended investigation.

### Verified along the way (attempt 2)
- Aspire project launching works on this machine (minimal AppHost).
- Both containers come up reliably: `mongo:8.3`, `confluentinc/confluent-local:8.2.0`.
- Dashboard serves; AppHost starts with no exported env vars.
