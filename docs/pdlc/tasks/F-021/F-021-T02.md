The headline defect. IdentityService.cs:135 called FindOneAndDeleteAsync on the whole CredentialEntity and :155 re-inserted it, so any fault between those lines destroyed email, password hash, role and reset flag irrecoverably — and because the re-insert sat inside catch when (IsMongoDown(ex)), THE DESTRUCTIVE PATH WAS THE HANDLED PATH: a transient blip returned a tidy 503 to a user whose account no longer existed. A mobile client refreshes hourly.
One round trip now: filter on refresh_token.hash = presented AND refresh_token.expiry > now AND (lock_until null OR <= now); update $set refresh_token. Single use is preserved by the old hash being in the FILTER — a replayed token matches nothing. The lock condition rides along, so AC-4 costs no extra query.
Both $or branches are required: in MongoDB a missing field satisfies no comparison operator, so lock_until <= now alone would never match an account that has never been locked, which is nearly all of them. Asserted against real Mongo, not just the double.
ORDERING TRAP, caught by the integration harness: minting the access token needs the email and role that only the matched document supplies, so the signing key must be read BEFORE the write or a key failure discovers itself after the client's token is already consumed. Reading it strictly (throwing) turned every REJECTED refresh into a 500 — the harness hosts Identity with no JWT_PRIVATE_KEY, and no unit test could see it because they all set the variable in their constructor. Resolution: read without throwing, throw only behind the match.
